BetterShift läuft als ein Container; das Image baut GitHub Actions und legt es in der GitHub Container Registry ab. Images nur für linux/amd64.

Compose-Datei

Auf Basis der docker-compose.yml des Repositories. Das Image ist das des Forks; die Datei im Repository zeigt noch auf das Upstream-Image.

services:
  bettershift:
    image: ghcr.io/flichb/bettershift:latest
    container_name: bettershift
    restart: unless-stopped
    ports:
      - "3000:3000"
    volumes:
      - ./data:/app/data
      - ./uploads:/app/public/uploads
    environment:
      TZ: "Europe/Vienna"
      DEFAULT_LOCALE: "de"
      BETTER_AUTH_URL: "https://dienste.firma.at"
      BETTER_AUTH_SECRET: "${BETTER_AUTH_SECRET}"
      TRUSTED_PROXY_HEADER: "X-Real-IP"

Hinweise zu den Einträgen:

  • Port 3000 (im Image gesetzt, mit Healthcheck auf /api/health). Davor gehört ein Reverse Proxy mit HTTPS.
  • ./data enthält die SQLite-Datenbank (sqlite.db). Das Verzeichnis muss erhalten bleiben, sonst gehen alle Daten verloren. Der Entrypoint korrigiert die Besitzrechte beim Start selbst.
  • ./uploads nimmt hochgeladene Dateien auf.
  • TZ=Europe/Vienna: Ohne diese Angabe läuft der Container in UTC und alle Uhrzeiten wären verschoben. Der Standard in .env.example ist Europe/Berlin.
  • DEFAULT_LOCALE=de: Sprache, wenn der Browser keine verlangt; zugleich die Sprache der Mails und der Feed-Texte. Standard in .env.example ist en.
  • BETTER_AUTH_URL: Die öffentliche Adresse, mit Schema und ohne Schrägstrich am Ende. Sie erscheint auch in den Links des persönlichen Feeds und in Tausch-Mails.
  • BETTER_AUTH_SECRET: Pflicht bei eingeschalteter Anmeldung. Erzeugen mit npx @better-auth/cli secret, außerhalb der Compose-Datei halten (z. B. in einer .env neben der Compose-Datei). Eine Änderung meldet alle Benutzer ab.
  • TRUSTED_PROXY_HEADER: Muss zum Reverse Proxy passen, weil die Ratenbegrenzung die Client-Adresse daraus liest. Den Header des eigenen Proxys eintragen (Caddy, nginx, Traefik: X-Real-IP; Cloudflare: CF-Connecting-IP; der Wert im Beispiel ist anzupassen). Hinter genau einem Proxy mit unbekanntem Header darf die Variable leer bleiben (dann gilt der letzte Eintrag von X-Forwarded-For). Ohne Proxy (direkt erreichbar) muss sie none sagen, sonst kann der Client seine Adresse frei wählen. Die Erläuterung steht in .env.example.
  • Weitere Variablen: .env.example erklärt alle mit ihren Standardwerten. Die Outlook-Variablen stehen in OUTLOOK_SETUP.md.

Alternativ lässt sich statt environment: wie in der Datei des Repositories eine .env per env_file: einbinden.

Datensicherung

Gesichert werden muss das Verzeichnis ./data (die SQLite-Datei). Nimm es ins Server-Backup auf. Damit die Datei konsistent ist, entweder

  • den Container kurz anhalten (docker compose stop), ./data kopieren, wieder starten (docker compose start), oder
  • im laufenden Betrieb auf dem Host mit sqlite3 data/sqlite.db ".backup 'sicherung.db'" eine konsistente Kopie ziehen. Das sqlite3-Programm ist im Image nicht enthalten, es läuft auf dem Host.

./uploads gehört ebenfalls ins Backup, sofern Dateien hochgeladen werden.

Bestehende Instanz aktualisieren

So bringst du eine bereits laufende Instanz auf einen neuen Stand. Die Daten in ./data bleiben dabei erhalten.

Woher neue Versionen kommen. GitHub Actions baut die Images des Forks und legt sie unter ghcr.io/flichb/bettershift ab:

TagEntsteht durchGedacht für
latestein Release (Git-Tag vX.Y.Z, angelegt mit npm run release:patch, release:minor oder release:major)den produktiven Betrieb
vX.Y.Z, vX.Y, vXdasselbe Releaseeine fest eingestellte Version
devjeden Push auf main, also jeden zusammengeführten Pull RequestTestinstanzen
pr-<Nummer>einen Pull Request aus diesem Repositorydas Ausprobieren vor dem Zusammenführen

Eine Änderung auf einem Feature-Branch, z. B. feat/rotation-generator, erreicht den Server also erst, wenn der Pull Request nach main zusammengeführt ist (dann dev) und danach ein Release erstellt wurde (dann latest und vX.Y.Z).

Empfehlung: Version fest einstellen. Trag in der Compose-Datei statt latest die Version ein, z. B. image: ghcr.io/flichb/bettershift:v3.3.1. Dann aktualisiert sich nichts unbemerkt, ein Update ist eine bewusste Änderung dieser Zeile, und für ein Zurück kennst du die alte Version.

Vorher prüfen.

  1. Welche Version läuft gerade: https://<deine-adresse>/api/version im Browser aufrufen oder auf dem Server docker compose images ausführen.
  2. Die Release-Notizen der neuen Version auf GitHub (Reiter „Releases" des Repositories) und UPGRADING.md lesen. Dort steht, ob eine Version Handgriffe verlangt, z. B. neue Umgebungsvariablen oder ein zusätzliches Volume.
  3. Einen ruhigen Zeitpunkt wählen. Während des Neustarts ist die App etwa eine Minute nicht erreichbar.

Schritte. Auf dem Server im Verzeichnis der Compose-Datei:

  1. Backup ziehen (siehe Datensicherung), z. B.:

    docker compose stop
cp -a data "data-backup-$(date +%Y%m%d)"

  2. Bei fest eingestellter Version die Zeile image: in der Compose-Datei auf die neue Version ändern. Bei latest entfällt dieser Schritt.

  3. Neues Image holen und starten:

    docker compose pull
docker compose up -d

  4. Start beobachten:

    docker compose logs -f bettershift

    Die Migrationen laufen beim Start von selbst (siehe unten). Wenn „Ready" erscheint, ist der Server bereit; mit Strg+C beendest du die Anzeige, der Container läuft weiter.

  5. Kontrollieren: /api/version zeigt die neue Nummer, /api/health meldet "status": "healthy", und Anmeldung, Kalender und /swaps funktionieren.

  6. Alte Images aufräumen (optional): docker image prune.

Migrationen. Das Image startet mit node scripts/migrate.mjs && node server.js. Erst werden die offenen Migrationen der Upstream-Tabellen eingespielt, danach die der Fork-Tabellen (Ordner drizzle/fork, eigene Verwaltungstabelle); danach startet der Server. Ein manueller Migrationsschritt ist nicht nötig. Schlägt eine Migration fehl, startet der Server nicht, und docker compose logs bettershift zeigt den Grund.

Zurück auf die alte Version. Migrationen lassen sich nicht rückgängig machen. Ein Zurück geht deshalb nur zusammen mit dem Backup:

docker compose down
rm -rf data
cp -a "data-backup-JJJJMMTT" data
# in der Compose-Datei die alte Version bei image: eintragen
docker compose up -d

Alles, was seit dem Backup eingetragen oder getauscht wurde, ist danach verloren.

Image nicht abrufbar? Meldet docker compose pull „denied" oder „unauthorized", ist das Paket in der GitHub Container Registry privat. Entweder stellt man es auf GitHub unter „Packages" → „bettershift" → „Package settings" auf öffentlich, oder man meldet den Server einmalig mit einem Token an, das das Recht read:packages hat: docker login ghcr.io -u <github-benutzer>, als Passwort das Token.

Besonderheit beim Update auf die wechselnden Paare (Oktober 2026). Ab dieser Version mischt der Generator die Paare ab der zweiten Runde neu (siehe Rotation anlegen). Bereits erzeugte Dienste bleiben, bis du die Rotation das nächste Mal generierst. Beim nächsten „Generieren" werden alle künftigen, nicht getauschten Plätze neu verteilt; getauschte Plätze bleiben gesperrt. Deshalb:

  1. Nach dem Update unter /rotations zuerst die „Vorschau" ansehen und erst dann „Übernehmen".
  2. Ist Outlook eingeschaltet, aktualisieren sich die Termine danach von selbst; die Betroffenen bekommen geänderte Einladungen bzw. Absagen.
  3. Das Team vorher kurz informieren, dass sich künftige Dienste verschieben.

Besonderheit beim Update auf „Ein Eintrag pro Person" (Oktober 2026). Jeder Platz hat jetzt einen eigenen Titel (Eintragsvorlage) und bei Outlook einen eigenen Termin. Nach dem Update auf diese Version sagt der erste Abgleich alle künftigen Termine im alten Format (ein Termin pro Dienst) ab und lädt pro Platz neu ein — jeder Teilnehmer bekommt einmalig eine Absage plus eine Einladung je künftigem Platz (bei einem Jahr voller Samstage mehrere Dutzend Mails pro Person), die Exchange teils verzögert zustellt. Informiere das Team vorher.

Besonderheit beim Update auf Jahresausgleich, Dienstfrei vor dem Dienst, Urlaub und Mindestbesetzung (Oktober 2026). Die Fork-Migrationen 0011 bis 0015 laufen beim Start von selbst; neue Umgebungsvariablen gibt es nicht. Bestehende Rotationen verhalten sich danach wie vorher: „Gerecht pro Kalenderjahr“ ist aus, „Dienstfrei liegt“ steht auf „nach dem Dienst“, die Mindestbesetzung ist aus. Erst wenn du eine dieser Einstellungen änderst, ändert sich etwas:

  1. Jahresausgleich einschalten: Das nächste Generieren verteilt alle nicht gesperrten künftigen Plätze neu. Zuerst die „Vorschau“ ansehen und das Team informieren; mit Outlook folgen geänderte Einladungen und Absagen.
  2. Dienstfrei auf „vor dem Dienst“ umstellen: Standard-Dienstfreie werden neu datiert (meist auf den Montag der Dienstwoche); die Inhaber bekommen Outlook-Aktualisierungen, verschobene außerhalb des neuen Bereichs zusätzlich eine Mail.
  3. Mindestbesetzung einschalten: Das Speichern verschiebt Standard-Dienstfreie still von vollen Tagen weg.
  4. Urlaub: Der Reiter „Urlaub“ auf /swaps steht sofort allen Teilnehmern zur Verfügung. Jede Genehmigung plant die Rotationen der Person neu und kann viele Outlook-Mails auslösen. Die zwei neuen Mail-Schalter sind für alle eingeschaltet.

Der Container hat nur eine Instanz: Starte nie zwei Container auf dieselbe ./data.

Erstinbetriebnahme

  1. Container starten und BETTER_AUTH_URL im Browser öffnen. Den ersten Benutzer registrieren: Er wird automatisch Superadmin.
  2. Teamkalender anlegen und in den Kalendereinstellungen die Anmeldungen einschalten.
  3. Preset „Samstagsdienst" anlegen: 09:30 bis 15:00 Uhr.
  4. Teilnehmer einladen bzw. registrieren lassen und den Kalender mit ihnen teilen, mit dem Bündel „Read" (siehe Rechte).
  5. Feiertagskalender anlegen: Kalender „Feiertage AT“ mit dem Abo webcal://www.wien.gv.at/spezial/daten/ics/feiertage.ics (siehe Feiertage und Schließtage).
  6. Unter /rotations die Rotation anlegen (siehe Rotation anlegen): Preset wählen, Teilnehmer in Reihenfolge, 2 pro Dienst, Periode Woche, Diensttag Sa, „Feiertagskalender“ „Feiertage AT“ und „Text bei Schließung“ „HeimkinoWelt geschlossen“. Dabei gleich festlegen: „Gerecht pro Kalenderjahr“ (bei neuen Rotationen vorgeschlagen), „Dienstfrei zum Dienst“ mit „Dienstfrei liegt“ (nach oder vor dem Dienst) und bei Bedarf „Mindestbesetzung an Werktagen“ (siehe Dienstfrei und Mindestbesetzung).
  7. Zeitraum wählen, „Vorschau" ansehen, dann „Übernehmen".
  8. Optional: Outlook nach OUTLOOK_SETUP.md einrichten und den Schalter der Rotation einschalten, zuerst im Trockenlauf.
  9. Das Team auf den persönlichen Kalender-Feed, die Tauschbörse und den Reiter „Urlaub“ hinweisen; die Anleitung für Mitarbeiter liegt in docs/anleitung/.

Outlook-Anbindung einrichten (Microsoft 365)

Diese Anleitung beschreibt, wie BetterShift an Microsoft 365 angebunden wird: Dienste von Rotationen erscheinen als Termine im Kalender von office@, und Tausch-Aktionen versenden Benachrichtigungs-Mails.

Überblick

Die Bedienung von Rotationen, Tauschbörse und persönlichem Kalender-Feed sowie den Betrieb beschreibt ROTATION_AND_SWAPS.md.

  • office@ ist der Organisator. Die App legt Termine im Kalender dieses Postfachs an, ändert sie und sagt sie ab. Pro Platz gibt es einen ganztägigen Termin (Status „Frei"); eingeladen ist nur der aktuelle Platzinhaber. Bei Tausch oder Umbesetzung wird der Termin des bisherigen Inhabers abgesagt und der neue Inhaber eingeladen. Nach dem Update auf diese Version sagt der erste Abgleich alle künftigen Termine im alten Format (ein Termin pro Dienst) ab und lädt pro künftigem Platz neu ein — jeder Teilnehmer bekommt einmalig eine Absage plus eine Einladung je künftigem Platz (bei einem Jahr voller Samstage mehrere Dutzend Mails pro Person), die Exchange teils verzögert zustellt. Informiere das Team vorher.
  • Weitere Termine derselben Rotation: Schließtage als ganztägiger Termin ohne Teilnehmer; jedes Dienstfrei (bei eingeschaltetem Dienstfrei) und jeder genehmigte Urlaub als ganztägiger Termin mit der Person als einzigem Teilnehmer und Status „Abwesend". Ein Urlaub gehört zur ersten Outlook-fähigen Rotation der Person (nach Namen sortiert). Einzelheiten in ROTATION_AND_SWAPS.md, Abschnitte 4a und 4b.
  • Exchange verschickt den Rest: Einladungen, Aktualisierungen und Absagen kommen von Exchange selbst, die App sendet sie nicht.
  • Benachrichtigungs-Mails werden über Graph sendMail von office@ verschickt: Tausch (neues Angebot, Direktanfrage, angenommen, abgelehnt, erzwungener Tausch, Ausgleich), Dienstfrei (Sperre, Vorschläge, Antworten, Erinnerung) und Urlaub (Anträge, Entscheidungen, direkte Einträge). Jeder Benutzer kann die Arten auf /swaps unter „Benachrichtigungen" einzeln abschalten.
  • Benötigt wird eine Entra-App mit Anwendungsberechtigungen (kein Benutzer-Login, kein Redirect).
  • Ohne Konfiguration bleibt alles aus; die App verhält sich wie ohne Phase 3. Pro Rotation gibt es zusätzlich den Schalter „In Outlook (office@) eintragen".
  • Bei AUTH_ENABLED=false sind Sync und Mails immer aus.

App-Registrierung (Entra Admin Center)

  1. Identität › Anwendungen › App-Registrierungen › Neue Registrierung.
  2. Name BetterShift, Kontotyp Nur dieses Organisationsverzeichnis (Single Tenant), keine Umleitungs-URI.
  3. Auf der Übersichtsseite notieren:
    • Verzeichnis-ID (Mandant) → OUTLOOK_TENANT_ID
    • Anwendungs-ID (Client) → OUTLOOK_CLIENT_ID
  4. Zertifikate & Geheimnisse › Neuer geheimer Clientschlüssel → den Wert (nicht die ID) sofort kopieren → OUTLOOK_CLIENT_SECRET.
  5. Ablaufdatum des Geheimnisses notieren und eine Kalendererinnerung davor setzen. Ein abgelaufenes Geheimnis zeigt sich als outlook.auth_failed im Audit-Log (siehe Fehlerbilder).

Berechtigungen

API-Berechtigungen › Berechtigung hinzufügen › Microsoft Graph › Anwendungsberechtigungen:

BerechtigungWofür
Calendars.ReadWriteTermine in office@ anlegen, ändern, absagen, nächtlich vergleichen
Mail.SendBenachrichtigungs-Mails von office@

Anschließend Administratorzustimmung erteilen.

Auf office@ beschränken (wichtig)

Anwendungsberechtigungen gelten standardmäßig für jedes Postfach im Mandanten. Ohne Einschränkung könnte die App (und jeder, der das Client-Secret kennt) alle Kalender lesen und in fremdem Namen Mails senden. Deshalb auf office@ begrenzen, mit Exchange Online RBAC for Applications (PowerShell, nach Connect-ExchangeOnline):

New-ServicePrincipal -AppId <OUTLOOK_CLIENT_ID> -ObjectId <Objekt-ID der Unternehmensanwendung> -DisplayName "BetterShift"
New-ManagementScope -Name "BetterShift office" -RecipientRestrictionFilter "PrimarySmtpAddress -eq 'office@firma.at'"
New-ManagementRoleAssignment -App <OUTLOOK_CLIENT_ID> -Role "Application Calendars.ReadWrite" -CustomResourceScope "BetterShift office"
New-ManagementRoleAssignment -App <OUTLOOK_CLIENT_ID> -Role "Application Mail.Send" -CustomResourceScope "BetterShift office"
Test-ServicePrincipalAuthorization -Identity <OUTLOOK_CLIENT_ID> -Resource office@firma.at

Die Objekt-ID der Unternehmensanwendung steht unter Identität › Anwendungen › Unternehmensanwendungen › BetterShift (nicht die Objekt-ID der App-Registrierung). Test-ServicePrincipalAuthorization sollte für office@ InScope = True melden und für ein anderes Postfach False.

Danach die mandantenweiten Graph-Anwendungsberechtigungen aus dem vorigen Abschnitt wieder entfernen. Die RBAC-Zuweisung erteilt die Rechte bereits eingeschränkt; solange die mandantenweite Zustimmung besteht, gilt sie weiterhin für alle Postfächer.

Wartezeit: RBAC-Zuweisungen in Exchange brauchen oft bis zu etwa 30 Minuten, bis sie wirken. Ein früher outlook.auth_failed direkt nach der Einrichtung ist daher normal; der Sync versucht es nach der Pause von selbst erneut.

Hintergrund: Microsoft-Artikel „Role Based Access Control for Applications in Exchange Online" (learn.microsoft.com).

Konfiguration

Die Variablen stehen mit Erklärung in .env.example (Abschnitt „[fork] Outlook / Microsoft 365"):

VariableBedeutung
OUTLOOK_TENANT_IDVerzeichnis-ID (Mandant)
OUTLOOK_CLIENT_IDAnwendungs-ID (Client)
OUTLOOK_CLIENT_SECRETWert des Clientschlüssels
OUTLOOK_ORGANIZERPostfach des Organisators, z. B. office@firma.at
OUTLOOK_SYNC_INTERVAL_SECONDSScan-Intervall, Standard 60, Minimum 15
OUTLOOK_DRY_RUNtrue = Graph-Aufrufe nur loggen; braucht nur OUTLOOK_ORGANIZER

Die ersten vier sind Pflicht; fehlt eine, bleibt der Sync aus. docker-compose:

services:
  bettershift:
    environment:
      OUTLOOK_TENANT_ID: "00000000-0000-0000-0000-000000000000"
      OUTLOOK_CLIENT_ID: "00000000-0000-0000-0000-000000000000"
      OUTLOOK_CLIENT_SECRET: "${OUTLOOK_CLIENT_SECRET}"
      OUTLOOK_ORGANIZER: "office@firma.at"

Das Secret besser in einer .env-Datei neben der Compose-Datei oder als Docker-Secret halten, nicht im Klartext einchecken. Danach den Container neu starten (docker compose up -d).

Die Anmelde-E-Mail eines Benutzers muss seine Microsoft-365-Adresse sein; sie wird als Teilnehmer- und Empfängeradresse verwendet.

Testen

  1. Trockenlauf: OUTLOOK_ORGANIZER=office@example.test, OUTLOOK_DRY_RUN=true, OUTLOOK_SYNC_INTERVAL_SECONDS=15 setzen. Beim Einschalten des Schalters einer Rotation erscheint im Server-Log je künftigem Platz eine Zeile [Outlook dry-run] create … (ganztägig, Status Frei, ein Teilnehmer); ein Tausch erzeugt ein cancel an den bisherigen und ein create (Einladung) für den neuen Inhaber sowie ein update am Termin des Partners (Zeile „Mit: …"), dazu mail "…"; Ausschalten erzeugt cancel.
  2. Echt: Dry-Run abschalten und die vier Pflichtvariablen setzen. Den Schalter für eine Rotation aktivieren und prüfen:
    • Im office@-Kalender steht pro künftigem Platz ein ganztägiger Termin (Status Frei).
    • Ein Teilnehmer hat die Einladung im Posteingang.
    • Zwei Dienste tauschen lassen: Die Absagen an die bisherigen und die Einladungen an die neuen Inhaber (plus Aktualisierung der Partner-Termine) kommen innerhalb etwa einer Minute.
    • Ein Angebot erzeugt eine Mail von office@ an die richtigen Empfänger.
    • Bei eingeschaltetem Dienstfrei: Der Inhaber hat einen ganztägigen Dienstfrei-Termin (Status Abwesend); nach „Verschieben" wandert er auf den neuen Tag.
    • Einen Urlaub für einen Teilnehmer eintragen: Er bekommt einen ganztägigen Urlaubs-Termin (Status Abwesend) und eine Mail; betroffene Dienste werden abgesagt bzw. neu eingeladen. Storno entfernt den Termin wieder.
    • Eine Rotation ausschalten, die Schließeinträge hat: Der Schließtermin (ohne Teilnehmer) muss aus dem Kalender verschwinden. Graph lehnt die Absage dafür mit 400 ab; die App löscht ihn dann stattdessen.
  3. Erst danach weitere Rotationen aktivieren.

Grenzen

  • Eine Serverinstanz. Der Sync-Worker läuft im Prozess; mehrere Replikas würden doppelt synchronisieren.
  • Mails werden mindestens einmal zugestellt. Stürzt der Server zwischen dem Versand und dem Speichern des Status ab, kann eine Mail ein zweites Mal gesendet werden.
  • Mails werden in der Sprache DEFAULT_LOCALE verschickt, nicht pro Empfänger.
  • Keine Übernahme bestehender Termine: Termine, die schon von Hand in office@ stehen, werden weder erkannt noch verknüpft. Die Rotation sollte in einem Zeitraum ohne manuelle Dienst-Termine starten.
  • Vergangene und bereits begonnene Dienste werden nie angefasst.
